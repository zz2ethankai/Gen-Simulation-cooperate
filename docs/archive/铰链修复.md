# 通用铰链资产结构修复规范

## 背景

SimBox 中的 `open` / `close` 类 skill 对铰链资产有一套隐含结构约定。现有 microwave
类资产基本符合这套约定，因此可以被 `ArticulatedObject`、KPAM、cuRobo、PhysX contact
view 和 Nav2 static map exporter 同时消费。

如果新资产虽然是合法 USD/Physics articulation，但不符合这套结构约定，就会出现“资产能加载，
但导航地图、运动规划或 contact sensor 不能正确处理”的问题。以 refrigerator CAD 资产为例：

- 资产使用多 link 扁平结构，例如 `cabinet_body`、`left_door`、`right_door`、`freezer_drawer`。
- 关节位于 `/object_name/joints/body_to_left_door` 这类非 microwave 风格路径。
- 碰撞体位于各 link 的 `collisions/*/box` 下，且碰撞体父 Xform 的 `purpose=guide`。
- 部分 Cube 的尺寸写在父 Xform 的 `xformOp:scale` 上，Cube prim 自身没有 `xformOp:scale`。

这些结构会触发两个问题：

- cuRobo 的 USD obstacle parser 直接读取 Cube prim 自身的 `xformOp:scale`，若缺失会报
  `TypeError: 'NoneType' object is not iterable`。
- Nav2 静态地图导出器当前使用 default-purpose bbox cache 栅格化 collision geometry。
  如果 collision prim 处在 `purpose=guide` 父级下，bbox 可能为空，导致障碍物不会进入
  `map.pgm`。

因此，修复不应只改 task YAML，也不应只在 skill 里堆兼容逻辑。最终修复点应在资产侧：
将所有单门铰链资产统一转换为 microwave 风格的 `/instance/base + /instance/contact_link +
/instance/contact_link_revolute` 结构，并保证碰撞几何可被标准 USD bbox、cuRobo 和 Nav2
地图生成流程直接读取。标注文件可以由仓库内工具基于资产结构生成，不作为资产制作方的主要交付项。

## 参考结构

现有 microwave 资产的有效结构如下：

```text
/root
/root/instance
/root/instance/base
/root/instance/contact_link
/root/instance/contact_link_revolute
```

加载到任务后，SimBox 会将 `/root` 映射为对象名。例如对象名为
`silver_french_door_refrigerator` 时，runtime 路径应为：

```text
/silver_french_door_refrigerator/instance
/silver_french_door_refrigerator/instance/base
/silver_french_door_refrigerator/instance/contact_link
/silver_french_door_refrigerator/instance/contact_link_revolute
```

## 目标 USD 层级

每个铰链资产应输出为“单目标运动部件”的 articulation。无论资产是 microwave、fridge、
cabinet、drawer、washer door 还是其他可开合对象，USD 层级都应满足：

```text
/root                                           Xform, defaultPrim
/root/instance                                  Xform, ArticulationRootAPI
/root/instance/base                             Xform, RigidBodyAPI
/root/instance/contact_link                     Xform, RigidBodyAPI
/root/instance/contact_link_revolute            PhysicsRevoluteJoint
```

`/root/instance/base` 包含所有不随目标运动部件运动的部分：

- 固定外壳、柜体、框架、墙面连接部分。
- 其他非目标运动部件。如果当前资产只用于打开左门，则右门应归入 `base`。
- 内部隔板、背板、固定装饰件、固定把手或其他不会随目标关节运动的组件。
- 上述固定部分对应的 visual geometry 和 collision geometry。

`/root/instance/contact_link` 只包含当前 skill 要操作的运动部件：

- 门板、抽屉面板、盖板或其他被打开/关闭的主体。
- 该运动部件上的把手、按钮、装饰条、显示面板。
- 该运动部件对应的 visual geometry 和 collision geometry。

如果一个真实物体有多个可操作关节，推荐按 skill 目标拆成多个单目标资产，而不是在一个
资产中暴露多个 `contact_link`：

```text
asset_left_door/instance.usd
asset_right_door/instance.usd
asset_drawer/instance.usd
```

其中：

- `asset_left_door` 的 `contact_link` 为左门，其余部分归入 `base`。
- `asset_right_door` 的 `contact_link` 为右门，其余部分归入 `base`。
- `asset_drawer` 的 `contact_link` 为抽屉，其余部分归入 `base`。

这样可以与 microwave 的单 `contact_link` skill/Kps 约定保持一致。

## Physics API 要求

`/root/instance` 必须应用 `UsdPhysics.ArticulationRootAPI`。

`/root/instance/base` 和 `/root/instance/contact_link` 必须应用
`UsdPhysics.RigidBodyAPI`。推荐保持以下基础属性有效：

```text
physics:rigidBodyEnabled = true
physics:kinematicEnabled = false
physics:startsAsleep = false
```

`/root/instance/contact_link_revolute` 必须是 `PhysicsRevoluteJoint`，并满足：

```text
physics:body0 = /root/instance/base
physics:body1 = /root/instance/contact_link
physics:jointEnabled = true
physics:collisionEnabled = false
```

关节轴和范围按目标运动部件的真实关节配置：

```text
physics:axis = X/Y/Z，按实际局部坐标系确定
physics:lowerLimit = 0
physics:upperLimit = 目标最大打开角度，例如 90 或 120
```

如果使用 drive，drive 参数应只用于稳定初始状态，不应与 skill 的开门控制冲突。

## 碰撞几何要求

碰撞几何必须能被以下方式直接计算出非空 bbox：

```python
UsdGeom.BBoxCache(Usd.TimeCode.Default(), [UsdGeom.Tokens.default_])
```

因此碰撞几何应满足：

- 碰撞 prim 自身带 `UsdPhysics.CollisionAPI`。
- 碰撞 prim 的 `purpose=default`。
- 碰撞 prim 的所有父级也不应使用 `purpose=guide` 隔离碰撞几何。
- 不要依赖 `purpose=guide` 的父 Xform 来组织 collision proxy。
- 碰撞 Mesh/Cube 的 bbox 在 default-purpose cache 下必须非空。

推荐组织方式与 microwave 一致：

```text
/root/instance/base/Component_0
/root/instance/base/Component_1
/root/instance/contact_link/Component_0
/root/instance/contact_link/Component_1
```

也可以保留语义化名字，但路径必须位于 `base` 或 `contact_link` 之下，且 default purpose
可见：

```text
/root/instance/base/static_body_collision_0
/root/instance/base/static_side_panel_collision_0
/root/instance/contact_link/moving_panel_collision_0
/root/instance/contact_link/handle_collision_0
```

不推荐使用以下结构：

```text
/root/static_body/collisions/body_top_cap/box
/root/left_door/collisions/left_door_panel/box
/root/right_door/collisions/right_door_panel/box
/root/joints/body_to_left_door
```

这类结构的问题不是“路径名称不好看”，而是它绕开了当前 SimBox skill 和 Kps 的默认约定：
`base`、`contact_link` 和 `contact_link_revolute` 不再能被直接定位，碰撞体也可能因为
`purpose` 或 bbox 计算方式被地图和规划模块跳过。

## Cube scale 要求

如果碰撞体或视觉体使用 `UsdGeom.Cube`，Cube prim 自身必须具备有效的
`xformOp:scale`。

不允许只在父 Xform 上写尺寸，而让 Cube prim 自身缺失 `xformOp:scale`。错误示例：

```text
/root/instance/base/collision_part       Xform, xformOp:scale=(0.4, 0.2, 0.8)
/root/instance/base/collision_part/box   Cube, no xformOp:scale
```

推荐写法：

```text
/root/instance/base/collision_part       Xform, xformOp:scale=(1, 1, 1)
/root/instance/base/collision_part/box   Cube, xformOp:scale=(0.4, 0.2, 0.8)
```

或者直接使用 Mesh 碰撞体，保证 Mesh prim 带 `CollisionAPI` 且 default-purpose bbox 非空。

## 验收标准

资产制作完成后，需要通过以下检查。

1. USD stage 默认 prim 有效：

```text
defaultPrim = /root
```

2. 必须存在以下 prim：

```text
/root/instance
/root/instance/base
/root/instance/contact_link
/root/instance/contact_link_revolute
```

3. Physics 关系正确：

```text
/root/instance/contact_link_revolute.physics:body0 -> /root/instance/base
/root/instance/contact_link_revolute.physics:body1 -> /root/instance/contact_link
```

4. 所有参与导航障碍的 collision prim 在 default-purpose bbox cache 下 bbox 非空。

5. 所有 Cube prim 自身都有有效 `xformOp:scale`。

6. 资产中目标运动部件的把手或接触区域具有稳定几何，能够由工具从 `contact_link` 的 bbox
   或 handle 语义命名中推断接触点。

7. SimBox 加载后，Nav2 导出的 `map.pgm` 中能够看到该铰链资产的占用区域。

## 修复边界

应该修复的位置：

- 资产 USD 层级：统一为 `/root/instance/base`、`/root/instance/contact_link`、
  `/root/instance/contact_link_revolute`。
- 资产 Physics API：确保 articulation root、rigid body、joint body relationship 正确。
- 资产 collision geometry：确保碰撞 prim 带 `CollisionAPI`、default purpose 可见、bbox 非空。
- 资产 Cube transform：确保 Cube prim 自身具备有效 `xformOp:scale`。
- 资产命名和几何组织：确保工具可以从 `base`、`contact_link` 和 joint 自动生成标注。

不应该作为最终修复的位置：

- 不应只在 task YAML 中改路径来规避资产结构问题。
- 不应依赖 Nav2 exporter 特判某个资产名。
- 不应依赖 cuRobo parser 特判某种 CAD 导出结构。
- 不应让 skill 逻辑同时支持大量互不兼容的 link 命名规范。

runtime 兼容逻辑可以作为过渡方案，但长期应以资产结构统一为准。

## 与当前临时修复的关系

当前代码侧临时修复包括：

- `scripts/simbox/generate_hinge_articulation_kps.py` 中的 `normalize_cube_scales()`，用于补齐
  Cube 自身 `xformOp:scale`。
- `workflows/simbox/core/tasks/banana.py` 中对 articulated object
  `forbid_collision_paths` 的读取和 contact sensor pattern 合并。
- `workflows/simbox/core/objects/articulated_object.py` 中保存
  `forbid_collision_paths`。

这些修复用于让现有 CAD 资产能继续运行，但不是最终资产结构目标。最终目标应是所有单门/单抽屉/
单盖板类铰链资产都输出 microwave 风格的
`/instance/base + /instance/contact_link + /instance/contact_link_revolute` 结构，从资产层面消除
对象类别专用兼容逻辑。资产端不需要手写 Kps 标注文件；只需要保证 USD 结构稳定、命名清晰、碰撞
和关节信息完整，标注可由工具生成。
